# DT-006: Add Transition Edges to Graph

**Status:** Planned  
**Date:** 2026-08-31  
**Phase:** 1 (Foundation → Production-Ready ETL)  
**Depends on:** DT-005 (Graph Node Snapping and Raw Pathway Graph)  
**Blocks:** DT-007 (Contract Degree-2 Chains)

---

## 1. Objective

Augment the raw pathway-only graph from DT-005 with 63 transition features (stairs and elevators), creating 126 bidirectional directed edges that connect nodes across vertical levels. Mark all transition endpoints as protected from contraction. Validate cross-level connectivity for both default (stairs + elevators) and accessible (elevators only) routing profiles. Produce `build/graph_with_transitions.pkl` as the complete uncontracted routing graph.

---

## 2. Context

### 2.1 Inputs

- `build/graph_raw.pkl` from DT-005: NetworkX MultiDiGraph, 15,582 nodes, 44,826 pathway arcs (mode='pathway' only), no transition edges yet
- `build/node_map.pkl` from DT-005: 44,978 snapped endpoints (44,852 pathway + 126 transition), maps `(layer_prefix, feature_id, endpoint_role)` → `(x, y, vertical_order)` coordinate tuples
- `build/wayfinding.gpkg` from DT-003: `Transitions_26910` layer with 63 MultiLineString Z features having `TRANSITION_TYPE` (2=stairs, 4=elevator), `LEVEL_ID_FROM`, `LEVEL_ID_TO`, `VERTICAL_ORDER_FROM`, `VERTICAL_ORDER_TO`, `LENGTH_3D`
- [docs/01-data-findings.md §5](../01-data-findings.md#5-routing-network): 42 stairs features (type 2), 21 elevator features (type 4), all `TRAVEL_DIRECTION=1` (bidirectional), 2 express elevators span vertical_order 0→2
- [docs/02-system-design.md §4.2](../02-system-design.md#42-accessible-mode--exactly-what-it-does-and-does-not-claim): accessible routing = elevator-only (stairs excluded), no wheelchair certification implied
- [ADR-0004 §4](../adr/0004-graph-construction-and-node-identity.md): edge key convention `TR_{feature_id}` / `TR_{feature_id}_R`, node-map usage to avoid re-snapping

### 2.2 Outputs

- Updated `packages/wayfinding/src/wayfinding/etl/graph.py` with `add_transitions(graph, node_map, gpkg_path)` function
- `build/graph_with_transitions.pkl`: NetworkX MultiDiGraph with 15,587 nodes, 44,952 total arcs (44,826 pathway + 126 transition)
- `build/graph_with_transitions_stats.json`: metadata including transition counts by type, cross-level connectivity analysis per profile, protected node count, express elevator list
- Updated `Makefile` target `etl-graph-transitions` wrapping containerized execution
- Updated `packages/wayfinding/src/wayfinding/etl/run.py` CLI with `graph-transitions` subcommand

### 2.3 Scope and Non-Goals

**In scope:**
- Add transition edges to existing graph using node_map.pkl (no re-snapping)
- Parse TRANSITION_TYPE → mode mapping (2→stairs, 4→elevator) verified against GDB domain
- Mark transition endpoints with `is_transition_endpoint=True` node attribute (prevents DT-007 contraction)
- Measure cross-level connectivity for default (stairs + elevators) and elevator-only profiles;
  enforce the pinned-fixture baselines from ADR-0005 and report component-level diagnostics
- Handle express elevators (vertical_order delta >1) as single edges without intermediate hops
- Detect and fail on orphan transitions (endpoints not found in node_map)

**Out of scope (deferred to later tickets):**
- Degree-2 chain contraction (DT-007)
- Unit connector edges (DT-008)
- Unit-to-component catalog and origin/destination reachability decisions (DT-009)
- Elevator-wait cost modeling or profile-specific penalties (routing engine, Phase 2)

## 3. Acceptance Criteria

All criteria deterministic, testable, map 1:1 to §5 test list.

### AC1: Transition edge count and bidirectionality

- `add_transitions()` reads 63 transition features from `Transitions_26910` layer
- Creates **126 directed edges** (63 features × 2 directions, all `TRAVEL_DIRECTION=1` per data findings)
- Edge keys follow ADR-0004 convention: `TR_{feature_id}` (forward), `TR_{feature_id}_R` (reverse)
- Forward arc: `(start_node, end_node, key="TR_{fid}")` where start_node has vertical_order_from, end_node has vertical_order_to
- Reverse arc: `(end_node, start_node, key="TR_{fid}_R")` with same attributes except reversed geometry
- **Tests:**
  - `test_add_transitions_edge_count` — assert exactly 126 transition edges added (63 × 2)
  - `test_add_transitions_bidirectional` — for every `(u, v, key)` with key starting `TR_`, assert `(v, u, key + "_R")` exists

### AC2: Transition type mapping and mode attribute

- Edge attribute `mode` set from `TRANSITION_TYPE` field:
  - `TRANSITION_TYPE = 2` → `mode = 'stairs'` (42 features → 84 arcs)
  - `TRANSITION_TYPE = 4` → `mode = 'elevator'` (21 features → 42 arcs)
- Verified against GDB coded-value domain `DOM_NETWORK_TYPE` per data findings §5
- No other `TRANSITION_TYPE` values exist in source (no escalators type 5, no ramps type 3, no moving walkways type 6)
- **Tests:**
  - `test_transition_type_mapping_stairs` — assert all edges with `TRANSITION_TYPE=2` have `mode='stairs'`
  - `test_transition_type_mapping_elevator` — assert all edges with `TRANSITION_TYPE=4` have `mode='elevator'`
  - `test_transition_mode_counts` — assert 84 stairs arcs, 42 elevator arcs

### AC3: Edge attribute schema for transitions

- Every transition edge has attributes `{length_3d: float, mode: str, level_id_from: str, level_id_to: str, vertical_order_from: int, vertical_order_to: int, feature_id: str, geometry: LineString}`
- `level_id_from` / `level_id_to` constructed from `FACILITY_ID` + `LEVEL_NAME_FROM` / `LEVEL_NAME_TO` (matching DT-005 snap_nodes convention)
- `vertical_order_from` / `vertical_order_to` retrieved from `node_map` node ID (never from Z coordinate)
- `length_3d` from source `LENGTH_3D` field (100% populated per data findings)
- `geometry` is Shapely LineString from source 3D geometry; reverse arc geometry is `LineString(reversed(coords))`
- **Tests:**
  - `test_transition_edge_attributes_schema` — every transition edge has all 8 required keys
  - `test_transition_vertical_order_from_node_map` — vertical_order values match node ID tuples, not Z coordinates
  - `test_transition_reverse_arc_geometry` — reverse arc coordinates are `list(reversed(forward_coords))`

### AC4: Transition endpoint protection and node attributes

- All **85 unique** transition endpoint nodes (126 endpoint references) are marked with node attribute
  `is_transition_endpoint=True`
- Five transition-only nodes absent from `graph_raw.pkl` are added without re-snapping. Their `x`,
  `y`, and `vertical_order` come from the DT-005 node ID; `level_ids` and endpoint Z aggregates come
  from the transition source rows, yielding the same complete node-attribute contract as DT-005.
- Prevents DT-007 contraction: nodes with `is_transition_endpoint=True` are never collapsed
- **Tests:**
  - `test_transition_endpoints_protected` — assert all 85 unique transition endpoint nodes are protected
  - `test_transition_endpoints_exist_in_graph` — all 126 transition endpoint nodes from node_map now exist in graph (no longer isolated after adding edges)
  - `test_transition_only_nodes_preserve_attributes` — assert all five added nodes have the complete
    DT-005 node-attribute contract

### AC5: Express elevator handling (vertical_order delta > 1)

- Two elevator features span vertical_order 0→2 (data findings §5)
- Produce **single edges** (2 forward + 2 reverse = 4 arcs total) directly connecting vertical_order 0 and 2 nodes
- No intermediate hops or artificial nodes at vertical_order 1
- Express elevators have `vertical_order_to - vertical_order_from == 2` or `-2`
- **Tests:**
  - `test_express_elevators_no_intermediate_hops` — identify 2 express elevator features, assert each produces exactly 2 arcs (forward + reverse), no edges with vertical_order=1 endpoints
  - `test_express_elevator_vertical_order_delta` — assert express elevator edges have `abs(vertical_order_to - vertical_order_from) == 2`

### AC6: Cross-level connectivity — default profile (non-regression validation)

**Revised per ADR-0005** (Measured connectivity baseline and validation gates): The measured DT-005 pathway-only baseline has **855 connected components**, making a hard gate requiring exactly 1 component mathematically impossible. DT-006 validates **non-regression** instead.

- Graph filtered to `mode in ['pathway', 'stairs', 'elevator']` (default profile)
- Compute undirected connected component count (use `G.to_undirected()`)
- **Pinned-fixture validation**: Component count must equal **816** for the checked-in source fixture,
  down from the 855-component pathway-only baseline
- Generic validation must also prove `component_count <= baseline_component_count` and
  `components_bridged_by_transitions > 0`; this prevents a no-op implementation from passing
- If either condition fails, fail the build with component diagnostics
- Log component statistics: total count, largest component size, component size distribution
- **No hard connectivity requirement**: Build succeeds with 816 components (fragmentation is documented as a data-quality limitation per ADR-0005)
- Record in `graph_with_transitions_stats.json`:
  ```json

    "component_count": 816,
    "largest_component_size": 7436,
    "component_size_histogram": {"1": 234, "2-10": 128, "11-100": 45, "101-1000": 8, "1001+": 1},
    "pathway_only_baseline": 855,
    "components_bridged_by_transitions": 39
  }
  ```
- **Tests:**
  - `test_default_profile_non_regression` — synthetic graph asserts component count does not increase
    and at least one component is bridged
  - `test_default_profile_measured_baseline` — production fixture has exactly 816 components and 39
    bridged components
  - `test_default_profile_component_statistics` — verify stats JSON has required keys
  - `test_default_profile_no_hard_gate` — assert build succeeds with 816 components (not 1)

## 4. Implementation Steps

Work proceeds in this order, each step sized to ≤0.5 day.

### 4.1 Update graph.py with add_transitions() function signature and skeleton (0.25 day)

- Add function `add_transitions(graph: nx.MultiDiGraph, node_map: dict, gpkg_path: str) -> tuple[nx.MultiDiGraph, dict]`
- Load `Transitions_26910` layer with `ogr.Open(gpkg_path, 0)` (read-only)
- Return updated graph and stats dict (initially empty)
- No edge-adding logic yet — just layer read and iteration over 63 features
- Update `run.py` CLI with `graph-transitions` subcommand: load graph_raw.pkl, load node_map.pkl, call add_transitions(), save outputs

### 4.2 Implement transition type mapping and edge attribute extraction (0.5 day)

- For each transition feature, read fields: `FID`, `TRANSITION_TYPE`, `FACILITY_ID`, `LEVEL_NAME_FROM`, `LEVEL_NAME_TO`, `LENGTH_3D`, `geometry`
- Map `TRANSITION_TYPE` → mode: {2: 'stairs', 4: 'elevator'}
- Construct `level_id_from = f"{FACILITY_ID}_{LEVEL_NAME_FROM}"`, `level_id_to = f"{FACILITY_ID}_{LEVEL_NAME_TO}"`
- Look up start and end nodes in node_map using keys `("TR", fid, "start")` and `("TR", fid, "end")`
- Extract vertical_order from node ID tuples (third element)
- Extract geometry as Shapely LineString, compute reversed coordinates for reverse arc
- Build edge attributes dict per AC3

### 4.3 Add bidirectional transition edges to graph (0.5 day)

- For each transition, add two directed edges:
  - Forward: `graph.add_edge(start_node, end_node, key=f"TR_{fid}", **attrs)`
  - Reverse: `graph.add_edge(end_node, start_node, key=f"TR_{fid}_R", **attrs_reversed)` where `attrs_reversed["geometry"]` is reversed LineString
- Detect orphan transitions (KeyError on node_map lookup): log error with feature details, collect all orphans, raise ValueError at end if any found
- Count stairs arcs (84) and elevator arcs (42) for stats

### 4.4 Mark transition endpoints as protected (0.25 day)

- Collect all unique nodes referenced by transition edges (start and end of all 63 features)
- Add the five transition-only nodes absent from the raw graph. Populate `x`, `y`, and
  `vertical_order` from the snapped node ID and aggregate `level_ids`, `z_min`, `z_max`, and `z_mean`
  from transition endpoint source values; do not synthesize or re-snap coordinates.
- For each node, set attribute `graph.nodes[node_id]["is_transition_endpoint"] = True`
- Count protected nodes for stats (exactly 85 unique nodes for the pinned fixture)
- Preserve existing node attributes (x, y, vertical_order, level_ids, z_min/z_max/z_mean from DT-005)

### 4.5 Implement express elevator validation (0.25 day)

- Filter transition edges to mode='elevator'
- For each, compute `delta = abs(vertical_order_to - vertical_order_from)`
- If delta > 1, add to `express_elevators` list in stats with feature_id and vertical_order pair
- Assert no intermediate nodes at vertical_order between from and to (should be automatic from node_map lookup, but validate in test)
- Expect exactly 2 express elevator features (data findings)

### 4.6 Implement default profile connectivity check (0.5 day)

- Filter graph to edges with `mode in ['pathway', 'stairs', 'elevator']`
- Convert to undirected with `G_default = filtered_graph.to_undirected()`
- Compute `component_count = nx.number_connected_components(G_default)`
- Compare with the 855-component raw baseline and calculate the reduction.
- Fail if component count increases or no component is bridged.
- For the pinned production fixture, assert 816 components, largest size 7,436, and 39 bridged
  components; log component sizes and level IDs for audit.

### 4.7 Implement elevator-only profile connectivity check (0.5 day)

- Filter graph to edges with `mode in ['pathway', 'elevator']` (stairs excluded)
- Convert to undirected
- Compute component_count
- Compare with the same 855-component raw baseline; fail if component count increases or no elevator
  bridges a component.
- For the pinned fixture, assert 840 components, largest size 7,060, and 15 bridged components.
- Log a warning stating that this is elevator-only, stairs-excluded routing within connected regions;
  it is not wheelchair certification.
- Do not compute a vertical-order reachability matrix. DT-009 will map units to component IDs so
  query-time reachability is stated for actual origins and destinations.

### 4.8 Write graph_with_transitions_stats.json and serialize artifacts (0.25 day)

- Assemble stats dict per AC10 schema
- Write to `build/graph_with_transitions_stats.json` with indent=2 for readability
- Serialize graph to `build/graph_with_transitions.pkl` using `pickle.dump(graph, f, protocol=5)`
- Log summary: "Graph with transitions: {node_count} nodes, {edge_count} edges ({pathway_arcs} pathway, {stairs_arcs} stairs, {elevator_arcs} elevator)"

### 4.9 Update Makefile and run.py CLI (0.25 day)

- Add `Makefile` target:
  ```makefile
  .PHONY: etl-graph-transitions
  etl-graph-transitions:
      docker compose -f infra/docker-compose.yml run --rm etl \
          sh -c "pip install -e packages/wayfinding[dev] && python -m wayfinding.etl.run graph-transitions"
  ```
- Update `run.py` with subcommand `graph-transitions`:
  - Load `build/graph_raw.pkl` and `build/node_map.pkl`
  - Call `add_transitions(graph, node_map, "build/wayfinding.gpkg")`
  - Save outputs to `build/graph_with_transitions.pkl` and `build/graph_with_transitions_stats.json`

### 4.10 Write comprehensive test suite (1.5 days, RED before implementation)

- Test structure mirrors DT-005: module structure, function signatures, transition type mapping, edge attributes, bidirectionality, express elevators, connectivity checks, determinism, container execution, read-only boundaries

## 8. Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| **Transition endpoints missing from node_map** (snapping bug in DT-005) | Build fails, cannot add transition edges | Detect as AC8 orphan transition check; fail loudly with feature_id and coordinates; requires DT-005 fix and rebuild |
| **Elevator-only profile fragmented** (840 components) | Many origin/destination pairs have no elevator-only route | Not an error (AC7); log component metrics and an elevator-only, stairs-excluded warning. DT-009 maps units to components for honest query-time failures. |
| **Express elevators create incorrect topology** (vertical_order 0→2 requires intermediate vo=1 node) | Wrong route costs, instructions skip intermediate levels | AC5 validates single-hop edges; no intermediate nodes; test on real express elevator features (2 exist) |
| **Transition type mapping error** (wrong mode assignment, e.g. elevator marked as stairs) | Accessible routes use stairs, violates elevator-only contract | AC2 validates against GDB domain `DOM_NETWORK_TYPE`; test mode counts (84 stairs, 42 elevators); grounded in data findings §5 |
| **Degree-2 contraction in DT-007 removes transition endpoints** | Vertical connections lost, graph becomes planar-only | AC4 marks endpoints protected with `is_transition_endpoint=True`; DT-007 must respect this flag |
| **Non-deterministic graph structure** | Cannot reproduce builds, invalidates testing | AC10 tests determinism; pickle same graph twice, assert equality; sort feature iteration by FID |

## 10. Rollback and Recovery

### Rollback strategy
- DT-006 produces new artifacts (`graph_with_transitions.pkl`, `graph_with_transitions_stats.json`), does not modify DT-005 outputs
- To rollback: delete DT-006 artifacts, revert code changes, DT-005 artifacts remain intact
- DT-007 (contraction) depends on DT-006 output; if DT-006 rollback needed, DT-007 must also be reverted

### Recovery from build failure
- **Orphan transition error (AC8)**: Indicates DT-005 node_map incomplete; requires DT-005 rebuild from clean DT-003/DT-004 state
- **Connectivity regression (AC6/AC7)**: Hard failure if adding a profile's transitions increases
  component count or bridges none; investigate node identity, missing edges, and source mapping
- **Pickle load error**: Container version mismatch (Shapely/NetworkX); rebuild DT-005 and DT-006 in same container session
