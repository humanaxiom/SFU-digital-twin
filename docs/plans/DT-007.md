## 1. Objective

Contract degree-2 pathway chain segments into single edges carrying full polyline geometry, reducing the over-noded graph from 44,952 directed arcs to approximately 2,500–4,000 directed arcs (~91.1–94.4% reduction). Preserve all junctions (physical pathway degree ≥3), transition endpoints, and unit-proximity nodes for DT-008 connector attachment. Output `build/graph_contracted.pkl` as the production routing graph ready for unit connectors.

**Note:** The 2,500–4,000 target is provisional, extrapolated from handoff phase estimates. RED fixture characterization in tests will measure actual deterministic output; any significant mismatch triggers plan/ADR review, not arbitrary threshold tuning.

### 2.3 Scope clarification: directed arcs vs physical chains

The phase plan states "reducing the graph from ~22k edges to ~3k" but requires disambiguation:

- **Source data:** 22,426 pathway features + 63 transition features = 22,489 total features
- **DT-006 output:** 44,952 **directed arcs** (each feature produces 2 arcs: forward + reverse)
  - 44,826 pathway arcs (22,413 pathway features × 2, accounting for 13 self-loops removed)
  - 84 stairs arcs (42 features × 2)
  - 42 elevator arcs (21 features × 2)
- **Contraction operates on chains:** A chain is a sequence of pathway-degree-2 nodes connected by pathway edges. Each chain is contracted into **2 directed arcs** (forward + reverse with reversed geometry).
- **Target:** 2,500–4,000 **total directed arcs** (provisional estimate from handoff phase):
  - Pathway arcs: 2,374–3,874 contracted pathway arcs (from 44,826 input pathway arcs)
  - Transition arcs: 126 arcs unchanged (84 stairs + 42 elevator)
  - Total: 2,500–4,000 directed arcs
  - **Reduction:** ~91.1–94.4% reduction from 44,952 total input arcs (or ~91.8–94.7% pathway-specific reduction from 44,826 pathway arcs to 2,374–3,874 output pathway arcs)
  - Mean edge length 8–15 m post-contraction (validates successful merging of 0.94 m micro-segments)
- **Protected arcs:** Transition edges (stairs, elevators) are **never contracted** — they remain as individual edges even if they form degree-2 chains with pathways. Only pathway-to-pathway chains are contracted.

**Key invariant:** The number of directed arcs in the output is always even (forward/reverse pairs), and equals 2× the number of physical contracted chains.

### 2.4 Protection rules (nodes never contracted)

**Critical:** This is a bidirectional MultiDiGraph. A physical interior chain node with two pathway neighbors has in_degree=2, out_degree=2, total directed degree=4. Protection and contraction eligibility must be defined using **physical pathway topology** (undirected distinct-neighbor count), not directed graph degree.

1. **Junctions:** Nodes with **≥3 distinct pathway neighbors** in the physical undirected topology (excludes parallel edges, counts unique adjacent nodes connected by pathway-mode edges)
2. **Transition endpoints:** All nodes with `is_transition_endpoint=True` attribute (85 nodes from DT-006)
3. **Unit-proximity nodes:** Nodes within 0.5 m (EPSG:26910 Euclidean distance) of any searchable unit centroid parsed from `centroid_26910` WKT field in `unit_26910` layer (reserved for DT-008 connector attachment)
   - Unit centroids read from `centroid_26910` text field (WKT POINT strings) in GeoPackage layer `unit_26910` (1,017 rows)
   - Parse WKT to extract (x, y) coordinates
   - Distance computed in EPSG:26910 (never EPSG:4326)
   - 0.5 m threshold ensures DT-008 connector edges are short (<1 m typical)
4. **Nodes adjacent to transition edges:** If a node is the endpoint of **any** transition edge (stairs or elevator), it is protected even if pathway-degree=2
   - Prevents contracting a pathway-transition-pathway sequence into a single edge
   - Preserves mode boundaries for routing profile filtering

**Contraction eligibility:** A node is contractible if and only if:
- **Exactly 2 distinct pathway neighbors** in the physical undirected topology (considering only mode='pathway' edges, ignoring edge multiplicity and direction)
- NOT `is_transition_endpoint=True`
- NOT within 0.5 m of any unit centroid
- NOT adjacent to any transition edge (no incident edges with mode='stairs' or mode='elevator')

**Physical topology view for eligibility:** To identify pathway-degree-2 nodes, construct an undirected view: for each node, collect the set of distinct neighboring nodes reachable via pathway-mode edges (collapse all parallel pathway edges, merge forward/reverse directions). If `len(distinct_pathway_neighbors) == 2`, the node is a chain candidate (subject to the other protection rules above).

### 2.5 Edge and geometry merge semantics

**Chain identification:**
- Start from a protected node, traverse degree-2 pathway nodes until reaching another protected node
- Collect all edges and intermediate nodes in traversal order
- Handle bidirectional pairs: for every forward chain `A→B→C→D`, there exists a reverse chain `D→C→B→A`
- Parallel edges: If multiple edges exist between the same protected node pair (MultiDiGraph allows this), each parallel edge family forms a separate chain

**Contracted edge attributes:**
```python
{
    "length_3d": float,  # Sum of all segment lengths in chain
    "mode": "pathway",   # All contracted edges are mode='pathway'
    "level_id": str,     # From first segment (all segments in chain must share level_id)
    "geometry": LineString,  # Concatenated coordinates from all segments
    "original_feature_ids": list[str],  # FIDs of all source pathway features in chain
    "contracted_segment_count": int,  # Number of original edges merged
}
```

**Geometry merge algorithm:**
- Forward chain `A→B→C→D` with geometries `g1: A→B`, `g2: B→C`, `g3: C→D`:
  - Merged geometry: `LineString(g1.coords[:-1] + g2.coords[:-1] + g3.coords)` (drop duplicate intermediate points)
- Reverse chain `D→C→B→A` with reversed geometries:
  - Compute independently by reversing the merged forward geometry: `LineString(reversed(forward_geom.coords))`
- Preserve Z coordinates throughout (all geometries are 3D LineStrings)

**Edge key convention:**
- Forward contracted edge: `PW_CONTRACTED_{chain_id}` where `chain_id` is deterministic (e.g., hash of sorted endpoint node IDs)
- Reverse contracted edge: `PW_CONTRACTED_{chain_id}_R`
- **Key pairing invariant:** When constructing reverse edges, generate the forward key first, then append `_R`. Do not parse existing keys to derive reverse keys (never split `_R` from a key that might already contain `_R`). Store forward/reverse pairs together during chain traversal so reverse key generation is explicit, not inferred.
- Original pathway edge keys (`PW_{fid}`, `PW_{fid}_R`) are discarded; contracted edges use new keys
- Transition keys (`TR_{fid}`, `TR_{fid}_R`) are preserved exactly as-is from DT-006; do not transform or recompute

**Level consistency validation:**
- All segments in a chain must have the same `level_id` (pathway chains never cross levels)
- If a chain spans multiple `level_id` values, fail the build with diagnostic listing the chain and its segments
- Transitions cross levels by definition but are never contracted

### 2.6 Deterministic behavior

- Chain traversal order: When a node has multiple degree-2 neighbors (shouldn't happen, but handle defensively), sort by node ID (x, y, vertical_order tuple) for deterministic order
- Protected node iteration: Sort protected nodes by node ID before starting chain traversal
- Feature ID collection: Sort `original_feature_ids` list before storing in edge attributes
- `chain_id` generation: Use deterministic hash (SHA256) of sorted endpoint node IDs + sorted original FIDs (ensures same chain gets same ID across runs)
- Random seed for shortest-path tests: Use `random.seed(42)` for reproducible node-pair selection

### 2.7 Non-goals (out of scope for DT-007)

- Unit connector edges (DT-008)
- Graph validation against routing profiles (DT-009)
- Instruction generation or bearing calculation (DT-010)
- Simplifying geometries (reducing vertex count within contracted edges) — preserve all vertices from source segments

## 4. Implementation Steps

Each step sized to ≤ half day; TDD workflow (test first, then implement).

### Step 1: Identify unit-proximity protected nodes (1–2 hours)

- Read `unit_26910` layer from GeoPackage using OGR
- Extract centroid coordinates from `centroid_26910` text field (WKT POINT strings, 1,017 rows)
- Parse WKT to (x, y) tuples in EPSG:26910
- For each unit centroid, find all graph nodes within 0.5 m Euclidean distance in EPSG:26910
- Return set of protected node IDs
- **Test:** `test_identify_unit_proximity_nodes_measured` — measure actual protected node count (do not assert guessed 200-600 range); record measured baseline in fixture

### Step 2: Identify all protected nodes (1–2 hours)

- Junctions: For each node, compute **distinct pathway neighbors** in physical undirected topology (collapse parallel edges, merge forward/reverse, mode='pathway' only). If `len(distinct_pathway_neighbors) >= 3`, protect.
- Transition endpoints: nodes where `graph.nodes[node].get('is_transition_endpoint', False) == True`
- Unit-proximity nodes from Step 1
- Transition-adjacent nodes: nodes incident to any edge with `mode in ('stairs', 'elevator')`
- Return `protected_nodes: set[NodeID]`
- **Test:** `test_identify_protected_nodes_includes_all_categories` — assert junctions (physical degree ≥3), transition endpoints, unit-proximity, and transition-adjacent all present

### Step 3: Identify contractible nodes (1 hour)

- For each node, check:
  - Exactly 2 distinct pathway neighbors in physical undirected topology (mode='pathway', collapse parallel/bidirectional)
  - Node not in `protected_nodes`
- Return `contractible_nodes: set[NodeID]`
- **Test:** `test_contractible_nodes_disjoint_from_protected` — assert no overlap between contractible and protected
- **Test:** `test_contractible_nodes_pathway_degree_2` — for sample of 50 contractible nodes, manually verify physical pathway degree=2

### Step 4: Traverse chains from protected nodes (2–3 hours)

- For each protected node `start`:
  - For each incident pathway edge (u, v, k) where `u == start`:
    - Traverse forward from `v`, collecting edges and nodes, until hitting another protected node `end`
    - Collect chain: `[(start, n1, k1), (n1, n2, k2), ..., (nN, end, kN)]`
    - Store chain keyed by `(start, end, frozenset(original_fids))`
- Handle reverse chains: if forward chain `A→D` exists, reverse chain `D→A` is automatically identified by symmetry
- **Test:** `test_traverse_chains_returns_dict` — assert output is dict with chain metadata
- **Test:** `test_traverse_chains_no_loops` — assert no chain contains duplicate nodes (except start/end if self-chain, which shouldn't exist)

### Step 5: Merge geometries and compute contracted edge attributes (2–3 hours)

- For each chain:
  - Sum `length_3d` from all segments
  - Concatenate geometries: `LineString(g1.coords[:-1] + g2.coords[:-1] + ... + gN.coords)` (drop intermediate duplicates)
  - Collect `original_feature_ids` from all edges in chain
  - Store `contracted_segment_count = len(chain)`
  - Generate deterministic `chain_id` from sorted endpoint nodes + sorted FIDs
- Create forward edge `(start, end, f"PW_CONTRACTED_{chain_id}")` with merged attributes
- Create reverse edge `(end, start, f"PW_CONTRACTED_{chain_id}_R")` with reversed geometry
- **Test:** `test_merge_geometries_concatenates_coords` — mock chain, assert merged geometry equals expected concatenation
- **Test:** `test_contracted_length_sums_segments` — mock chain with known lengths, assert sum matches

### Step 6: Build contracted graph (2 hours)

- Create new `nx.MultiDiGraph()`
- Add all protected nodes with their attributes (copy from input graph)
- Add all contracted pathway edges from Step 5
- Add all transition edges (stairs, elevator) unchanged from input graph
- **Test:** `test_build_contracted_graph_preserves_transitions` — assert all 126 transition edges copied verbatim
- **Test:** `test_build_contracted_graph_node_attributes` — sample 10 nodes, assert attributes copied

### Step 7: Validate level consistency and output stats (1–2 hours)

- For each contracted edge with `contracted_segment_count > 1`:
  - Trace back to original segments
  - Assert all have same `level_id`
  - If mismatch, log diagnostic and fail build
- Compute stats:
  - Node count, edge count, mean degree
  - Contraction ratio: `(input_pathway_arcs - output_pathway_arcs) / input_pathway_arcs`
  - Mean edge length for mode='pathway'
  - Protected node counts by category (junctions, transition endpoints, unit-proximity, transition-adjacent)
  - Connected component counts per profile (default, accessible)
- **Test:** `test_validate_level_consistency_fails_on_cross_level_chain` — inject mock cross-level chain, assert build fails

### Step 8: Shortest-path validation (2 hours)

- Seed `random.seed(42)`
- Iterate deterministically through profile components containing at least two protected nodes and select connected protected-node pairs until exactly 20 pairs are collected
- For each pair:
  - Compute shortest path in input graph by `length_3d`
  - Compute shortest path in contracted graph
  - Fail validation if the pair is disconnected in either graph
  - Assert path lengths match within 0.01 m
- Fail validation if 20 connected protected-node pairs cannot be selected
- Record results in stats JSON: `shortest_path_validation: {pairs_tested, pairs_matched, max_delta_m}`
- **Test:** `test_shortest_path_validation_runs` — assert function executes without error
- **Test:** `test_shortest_path_validation_deterministic` — run twice with same seed, assert same pairs tested

### Step 9: Serialize outputs and CLI integration (1 hour)

- Serialize `graph_contracted.pkl` (pickle protocol 5)
- Write `graph_contracted_stats.json` with all stats from Step 7 + Step 8
- Add `contract_degree2_chains()` function signature to `graph.py`
- Add `run_graph_contract(output_dir: Path) -> int` entry point
- Update `run.py` CLI with `graph-contract` subcommand
- Update `Makefile` with `etl-graph-contract` target
- **Test:** `test_run_graph_contract_writes_artifacts` — assert pkl and json files created

## 7. Risks and Mitigations

| Risk | Impact | Mitigation |

## 9. Open Questions and Decisions

| Question | Resolution | Rationale |
|----------|-----------|-----------|
| **Should transition edges ever be contracted?** | **No.** Transitions (stairs, elevators) always remain as individual edges. | Routing profiles filter by mode (stairs excluded from accessible profile). Contracting a pathway-stairs-pathway sequence into one edge loses mode boundary. Also, transition geometries cross vertical_order levels; contraction assumes within-level chains. |
| **Should parallel edges between same protected nodes be merged?** | **No.** Preserve as distinct edges. | Parallel edges represent distinct physical pathways (e.g., two hallways between same junctions). Merging loses this distinction. MultiDiGraph handles parallel edges natively. If truly duplicates (same geometry, same FIDs), that's a DT-005 data error, not DT-007's problem. |
| **Should contraction simplify geometries (reduce vertex count)?** | **No.** Preserve all vertices. | Simplification (Douglas-Peucker, Visvalingam-Whyatt) risks losing corners or introducing geometric error. Instruction generation (DT-010) needs exact geometry for bearing calculation. Simplification can be done at rendering time (web client), not ETL. |
| **What if unit-proximity protection creates isolated degree-1 nodes?** | **Allow it.** These nodes are valid connector attachment points for DT-008. | A unit near the end of a hallway may protect a degree-1 node (cul-de-sac). This is correct behavior — DT-008 connects the unit to that node. |
| **Should contraction respect original edge direction (forward/reverse pairs)?** | **Yes.** Always contract forward and reverse chains together. | Contraction operates on undirected chains (sequences of degree-2 nodes), but output must preserve bidirectionality (every contracted edge has reverse pair with reversed geometry). Chain traversal identifies forward chains; reverse chains are implicit. |
| **What if shortest-path validation finds disconnected pairs?** | **Skip the pair, log warning, do not fail build.** | Graph has 816 components; disconnected pairs are expected. Validation ensures contraction preserves connectivity **within** components, not across components. If >50% of pairs are disconnected, that suggests non-random sampling bias — investigate seed or protected node selection. |

**No open blockers.** All ambiguities resolved; ready for implementation.
