# DT-005: Graph Node Snapping and Raw Graph Construction

**Status:** Planned  
**Date:** 2026-08-31  
**Phase:** 1 (Foundation → Production-Ready ETL)  
**Depends on:** DT-003 (Extract to GeoPackage), DT-004 (Normalise Tables)  
**Blocks:** DT-006 (Add Transition Edges), DT-007 (Contract Degree-2 Chains)

---

## 1. Objective

Snap all pathway and transition endpoints to a 1 cm grid in (x, y, vertical_order), then build a
**raw pathway-only graph** as a NetworkX MultiDiGraph with bidirectional edges. This establishes the
unified node space for the entire routing network and creates the horizontal pathway network that
DT-006 will augment with vertical transition edges.

---

## 2. Context

### 2.1 Inputs

- `build/wayfinding.gpkg` from DT-003:
  - `Pathways_26910`: 22,426 MultiLineString Z features with `LEVEL_ID`, `LENGTH_3D`,
    `TRAVEL_DIRECTION=1` (100% bidirectional, per data findings §5)
  - `Transitions_26910`: 63 MultiLineString Z features with `LEVEL_ID`, `TRANSITION_TYPE` (2=stairs,
    4=elevator), `VERTICAL_ORDER_FROM`, `VERTICAL_ORDER_TO`
- `build/wayfinding.gpkg` from DT-004:
  - `level_26910`: 11 rows mapping `level_id → vertical_order` (range [-2, 3])
- [docs/01-data-findings.md §5](../01-data-findings.md#5-routing-network): Raw pathways are
  over-noded (mean 0.94 m), all `TRAVEL_DIRECTION=1`, `LENGTH_3D` 100% populated

### 2.2 Outputs

- `packages/wayfinding/src/wayfinding/etl/graph.py` with:
  - `extract_endpoints(geometry) -> tuple[Coordinate, Coordinate]`
  - `snap_nodes(gpkg_path, level_lookup) -> tuple[node_map, node_attrs]`; `node_map` maps
    `(layer_prefix, feature_id, endpoint_role)` to `(x, y, vertical_order)`
  - `build_raw_graph(gpkg_path, node_map, node_attrs, level_lookup) -> tuple[nx.MultiDiGraph, dict]`
- `build/graph_raw.pkl` — NetworkX MultiDiGraph with ~22.5k bidirectional pathway edges (45k
  directed arcs) and ~15k nodes, **excluding transition edges** (those are DT-006's responsibility).
  Node IDs are snapped coordinate tuples `(x, y, vertical_order)` per ADR-0004.
- `build/node_map.pkl` — Serialized node_map for DT-006 to consume (avoids re-snapping transition
  endpoints). Contains all snapped endpoints (pathways + transitions), even those not yet in graph.
- `build/graph_raw_stats.json` — artifact metadata: node count, edge count, mean degree, isolated
  nodes (should be 0), self-loops removed (with FID list), ETL version, timestamp

### 2.3 Resolved ambiguities and boundary clarifications

| Question | Resolution | Evidence / Rationale |
|---|---|---|
| **DT-005 vs DT-006 ownership: who adds transition edges?** | **DT-005**: Snap all endpoints (pathways + transitions) to establish unified node space; build edges **only from pathways**. **DT-006**: Add transition edges to the already-snapped graph. | PHASE-1-ETL.md DT-005 description says "snap all pathway and transition endpoints" but DT-006 is titled "Add Transition Edges". Resolution: Snapping is a node-space operation (affects identity), edge-building is a graph-topology operation. DT-005 creates horizontal network + node space; DT-006 adds vertical connections. |
| **Undirected graph or DiGraph with bidirectional edges?** | **NetworkX MultiDiGraph** with every pathway edge added as two directed arcs (u→v and v→u), each with identical attributes. Transitions in DT-006 will also be bidirectional (126 arcs from 63 features). | PHASE-1-ETL.md says "raw undirected graph" but output specifies "NetworkX DiGraph, but with all edges bidirectional". Data findings §5 confirm `TRAVEL_DIRECTION=1` for all features. DiGraph is more flexible for future directed features (e.g., one-way doors, escalators) and aligns with DT-006 AC1 "63 directed edge pairs (126 edges)". |
| **MultiGraph or simple Graph/DiGraph?** | **NetworkX MultiDiGraph** — allows parallel edges between same node pair with distinct keys. | With 22,426 pathway segments snapped to 1 cm grid, multiple features will share endpoints (e.g., T-junctions where 3 segments meet same node). Before contraction (DT-007), parallel edges are expected and valid — they represent distinct pathway features. Edge key = `f"PW_{feature_id}"` for pathways. |
| **Node identity and coordinate snapping precision** | Node identity = `(round(x * 100) / 100, round(y * 100) / 100, vertical_order)`. Round x, y to **nearest centimeter (2 decimal places)** in EPSG:26910 metres. `vertical_order` retrieved from `level_id` via normalised `level_26910` table, never from Z coordinate. | Data findings §5: mean segment length 0.94 m, min 0.002 m. 1 cm grid (0.01 m) balances precision (won't merge distinct junctions <1 cm apart) with snapping effectiveness (merges micro-gaps from CAD export). ADR-0003 and spatial-invariants.instructions.md: "`vertical_order` is the authoritative level discriminator". |
| **Z coordinate handling** | Read Z from raw geometry, log min/max/mean per level to `build/graph_raw_stats.json`, **discard Z from node identity**. Store Z in node attributes as `z_min`, `z_max`, `z_mean` (mean of all features sharing that snapped node). | Data findings: all layers are 3D (hasZ=true), but Z is noisy. `vertical_order` is the reliable floor key. Z is preserved for future vertical-clearance analysis (e.g., "height under stairs") but does not affect routing. |
| **Geometry serialization in edge attributes** | Store as **Shapely LineString objects** (native Python objects) in the pickle. Pickle can serialize Shapely 2.x geometries directly. Do NOT convert to WKT/WKB — that loses in-memory efficiency and complicates DT-007 contraction. | Graph artifacts are internal ETL intermediates, not interop formats. Shapely objects are the natural representation for Python spatial operations. If WKT export is needed later, add a separate export function. |
| **Self-loop policy** | **Detect and exclude** — if `start_node == end_node` after snapping, log a warning with `feature_id`, level, and coordinates, increment a counter in `graph_raw_stats.json`, and skip adding the edge. | Self-loops break shortest-path algorithms and are likely CAD artifacts (e.g., a pathway feature with identical start/end after grid snapping). AC6 requires `len([e for e in G.edges if e[0] == e[1]]) == 0`. |
| **Edge attribute schema** | `{length_3d: float, mode: str, level_id: str, feature_id: str, geometry: LineString}`. `mode='pathway'` for all edges in DT-005 (transitions are DT-006). `length_3d` from source `LENGTH_3D` field (100% populated). `geometry` is the full 3D LineString from source (may have intermediate vertices). | PHASE-1-ETL.md AC3. `geometry` is required for DT-007 contraction (must merge geometries when collapsing chains) and DT-010 instruction generation (bearing calculations). |
| **Deterministic ordering for reproducibility** | When reading features from GeoPackage, sort by `feature_id` (FID) before processing. When iterating over snapped nodes, sort by `(x, y, vertical_order)`. Log all operations with feature counts to `graph_raw_stats.json` for audit. | Ensures identical graphs across runs and platforms. GDAL layer iteration order may be non-deterministic; explicit sorting enforces reproducibility. |
| **Isolated nodes (degree 0)** | Should be **zero** after DT-005. DT-005 snaps all endpoints (pathways + transitions) into `node_map`, but only adds nodes to the NetworkX graph when they have edges. Since DT-005 adds only pathway edges, only pathway endpoints appear in `graph_raw.pkl`. Transition endpoints exist in `node_map.pkl` but not in the graph until DT-006. If any node in the output graph has degree 0, log with coordinates and fail the build. | Per ADR-0004 §3: node-map (the universe of snapped coordinates) vs graph-membership (nodes with edges) are distinct. Zero isolated nodes in graph output ensures all pathway endpoints connect. Transition endpoints isolated in DT-005 is expected and correct. |
| **Data-QA connectivity check scope** | **Within-level connectivity only** for DT-005. Each level (filtered by `level_id`) should form 1–3 connected components (main network + possibly detached wings). Cross-level connectivity is DT-006's responsibility (requires transitions). | PHASE-1-ETL.md AC4 says "graph filtered to `mode in ['pathway','stairs','elevator']` has exactly 1 connected component" — but DT-005 has no stairs/elevators yet. Check is deferred to DT-006. |

## 3. Acceptance Criteria

All criteria are deterministic, testable, and map 1:1 to test cases (see §5 Test List).

### AC1: Node snapping correctness and vertical_order lookup

- Node identity is `(round_half_up(x, 2), round_half_up(y, 2), vertical_order)` where x, y are
  EPSG:26910 metres rounded to nearest 1 cm using round-half-up quantization:
  `floor(coord * 100 + 0.5) / 100` (per ADR-0004 §2a, avoids banker's rounding)
- Node IDs are the snapped coordinate tuples themselves (no separate UUID or sequential int)
  — deterministic, stable, and self-documenting (ADR-0004 §2b)
- `vertical_order` is retrieved from the normalised `level_26910` table by joining on `level_id`,
  never computed from Z coordinate
- Every pathway and transition endpoint maps to exactly one snapped coordinate in `node_map`
- Node attributes in the graph include: `{x, y, vertical_order, level_ids: set[str], z_min, z_max, z_mean}`
  - `level_ids` is the union of all `level_id` values from features touching that node (usually 1,
    but 2+ for cross-level junctions near transitions)
  - `z_min`, `z_max`, `z_mean` are the range and mean of Z coordinates from all raw endpoints that
    snapped to this node
- **Tests:**
  - `test_snap_nodes_precision` — verify x, y rounded to 0.01 m (2 decimal places)
  - `test_snap_nodes_vertical_order_from_level` — assert `vertical_order` matches
    `level_26910.vertical_order` for all nodes, never computed from Z
  - `test_snap_nodes_z_preserved_in_attributes` — every node has `z_min`, `z_max`, `z_mean`

### AC2: Raw graph structure and bidirectionality

- Graph is a **NetworkX MultiDiGraph** (supports parallel edges, directed arcs)
- Node count ~15,000 (rough estimate; depends on grid snapping deduplication)
- Edge count ~45,000 directed arcs (22,426 pathway features × 2 directions)
- Every pathway feature creates **two directed edges**: (start→end) and (end→start), both with
  identical attributes except `geometry` (reversed for backward arc)
- Edge keys follow ADR-0004 convention: `f"PW_{feature_id}"` for forward arc,
  `f"PW_{feature_id}_R"` for reverse arc (prefix=PW for pathways; DT-006 will use TR for transitions)
- **No transition edges** in DT-005 output (mode='stairs' or mode='elevator' edges are DT-006's
  responsibility)
- **Tests:**
  - `test_raw_graph_is_multidirected` — assert `isinstance(G, nx.MultiDiGraph)`
  - `test_raw_graph_node_count` — assert 10,000 < node_count < 20,000 (rough sanity bound)
  - `test_raw_graph_edge_count` — assert 40,000 < edge_count < 50,000 (2 × pathways)
  - `test_raw_graph_bidirectional` — for every `(u, v, key)` edge, assert `(v, u, key + "_R")` exists
  - `test_raw_graph_no_transition_edges` — assert all edges have `mode='pathway'`

### AC3: Edge attributes schema and completeness

- Every edge has attributes `{length_3d: float, mode: str, level_id: str, feature_id: str, geometry:
  LineString}`
- `mode='pathway'` for all edges (validated in AC2 test)
- `length_3d` is a float > 0, copied from source `LENGTH_3D` field (100% populated per data findings)
- `feature_id` is the string FID from source layer (e.g., `"12345"`)
- `geometry` is a Shapely LineString object (not WKT/WKB) with Z coordinates preserved
- **Reverse arc geometry** is `LineString(reversed(forward_geom.coords))` — coordinates in reverse
  order to match arc direction
- **Tests:**
  - `test_raw_graph_edge_attributes_schema` — every edge has exactly 5 required keys
  - `test_raw_graph_edge_mode` — all edges have `mode='pathway'`
  - `test_raw_graph_edge_weights_positive` — all `length_3d > 0` (PHASE-1-ETL AC5)
  - `test_raw_graph_edge_geometry_type` — all geometries are Shapely LineString instances
  - `test_raw_graph_reverse_arc_geometry` — for bidirectional pair, assert reverse arc coords are
    `list(reversed(forward_arc.coords))`

### AC4: Self-loop detection and exclusion

- **Zero self-loops** in output graph (PHASE-1-ETL AC6)
- If any pathway feature has `start_node == end_node` after snapping, log a warning with `feature_id`,
  `level_id`, snapped coordinates, and original endpoint coordinates
- Count of removed self-loops stored in `build/graph_raw_stats.json` under `self_loops_removed` with
  list of `feature_id` values
- Build succeeds even if self-loops are found (they are removed, not an error) — but the log must be
  visible for data-QA investigation
- **Tests:**
  - `test_no_self_loops` — assert `G.number_of_selfloops() == 0`
  - `test_self_loop_logging` — inject a mock pathway feature with identical endpoints, run snapping,
    assert warning logged and edge not added

### AC5: Isolated nodes and within-level connectivity

- **Zero isolated nodes** (degree 0) in the output graph
- Test `test_no_isolated_nodes` asserts `min(dict(G.degree()).values()) >= 1`
- If isolated nodes exist, log all with coordinates and `level_ids`, write to
  `graph_raw_stats.json`, and **fail the build** (indicates snapping bug or corrupted data)
- **Within-level connectivity** is informational only (not a hard requirement for DT-005):
  - For each `level_id`, extract subgraph of all edges with that `level_id`
  - Count connected components (undirected connectivity)
  - Log to `graph_raw_stats.json` as `connectivity_by_level: {level_id: {component_count: int,
    largest_component_size: int}}`
  - Record all 11 levels with positive node/component counts and largest-component size. The
    measured raw baseline ranges from 4 to 253 components per level; connectivity is not a hard
    gate until transitions and later graph construction stages are complete.
- **Tests:**
  - `test_no_isolated_nodes` — all nodes have degree ≥ 1
  - `test_within_level_connectivity` — all 11 levels are represented and satisfy
    `1 <= component_count <= node_count` and `1 <= largest_component_size <= node_count`

### AC6: Deterministic artifact serialization and reproducibility

- `build_raw_graph()` returns the same graph structure (same nodes, edges, attributes) when run
  twice on the same GeoPackage input
- Pickle serialization to `build/graph_raw.pkl` is deterministic (byte-identical output modulo
  timestamp) when sorting is applied
- `graph_raw_stats.json` includes:
  - `{etl_version, timestamp, node_count, edge_count, mean_degree, levels_processed: [list],
    self_loops_removed: int, self_loop_fids: [list], connectivity_by_level: {...},
    z_range_by_level: {level_id: {min, max, mean}}}`
- **Tests:**
  - `test_build_raw_graph_deterministic` — run `build_raw_graph()` twice on same input, assert node
    and edge sets are identical (pickle may differ due to dict ordering, but graph structure must match)
  - `test_graph_raw_stats_json_schema` — validate all required keys exist in stats JSON

### AC7: Container-only execution and read-only source boundary

- All code runs inside the `etl` Docker service (GDAL + Python 3.12)
- Source GeoPackage `build/wayfinding.gpkg` is read-only (no writes during graph construction)
- Output artifacts written only to `build/graph_raw.pkl` and `build/graph_raw_stats.json`
- Source geodatabase `C:\repos\sfudt\claude\dtwin-harness\data\IndoorWayfinding.gdb` never accessed
  (DT-003 already extracted it)
- **Tests:**
  - `test_container_execution` — verify `make etl-graph-raw` invokes Docker Compose, not host Python
  - `test_no_gdb_access` — mock filesystem, assert no reads to `IndoorWayfinding.gdb` path during
    DT-005 code execution

## 4. Implementation Steps

Work proceeds in this order, each step sized to ≤0.5 day. All steps are inside the container.

### Step 1: Create graph.py skeleton and level_id → vertical_order lookup (0.5 day)

- Create `packages/wayfinding/src/wayfinding/etl/graph.py`
- Add `load_level_lookup(gpkg_path: str) -> dict[str, int]` function:
  - Opens `build/wayfinding.gpkg` layer `level_26910` (11 rows)
  - Returns `{level_id: vertical_order}` dictionary
  - Validates all 11 level_id values from data findings §3 are present
- Add module docstring explaining DT-005 scope (snapping + pathway edges, no transitions yet)
- Add constants: `SNAP_PRECISION_CM = 1`, `EPSG_26910 = 26910`

### Step 2: Implement snap_nodes() function (1 day)

- Signature: `snap_nodes(gpkg_path: str, level_lookup: dict[str, int]) ->
  dict[tuple[str, str], tuple[float, float, int]]`
  - Returns `node_map: dict[(feature_id, endpoint_role), (x, y, vertical_order)]` where endpoint_role
    is "start" or "end"
  - Node ID is the snapped coordinate tuple itself (ADR-0004 §2b): no separate ID allocation
  - Also accumulates node attributes `dict[tuple[float, float, int], {level_ids: set, z_values: list}]`
    for computing z_min/z_max/z_mean per node
- Opens `Pathways_26910` and `Transitions_26910` layers from `build/wayfinding.gpkg`
- For each feature, extract start and end points:
  - For MultiLineString: start = first coord of first part, end = last coord of last part (ADR-0004 §5)
- Retrieve `vertical_order` from `level_lookup[feature.level_id]`; fail if `level_id` not found
- Round x, y with round-half-up: `snapped = (floor(x*100 + 0.5)/100, floor(y*100 + 0.5)/100, vertical_order)`
  (ADR-0004 §2a)
- Store in `node_map[(feature_id, "start")] = snapped_start` and `node_map[(feature_id, "end")] = snapped_end`
- Accumulate Z values and `level_id` in a separate `node_attrs[snapped]` dict for computing stats
- Return `node_map` (will be pickled for DT-006)

### Step 3: Implement build_raw_graph() — pathway edges only (1.5 days)

- Signature: `build_raw_graph(gpkg_path: str, node_map: dict, node_attrs: dict, level_lookup: dict)
  -> tuple[nx.MultiDiGraph, dict]`
  - Returns `(graph, stats)` where `stats` is the metadata dict for JSON export
- Create `G = nx.MultiDiGraph()`
- Do NOT pre-add nodes — NetworkX adds them on-demand when adding edges (ADR-0004 §3). This ensures
  zero isolated nodes (only pathway endpoints with edges appear in DT-005 graph).
- Open `Pathways_26910` layer, sort features by FID
- For each pathway feature:
  - Look up snapped start/end from `node_map[(fid, "start")]` and `node_map[(fid, "end")]`
  - If start == end (self-loop), log warning, increment `stats['self_loops_removed']`, continue
  - Read `length_3d` (use source field directly, no validation — ADR-0004 §6), `level_id`,
    `feature_id` (FID), geometry (LineString Z)
  - Create forward edge: `G.add_edge(start_node, end_node, key=f"PW_{feature_id}", length_3d=...,
    mode='pathway', level_id=..., feature_id=..., geometry=geom)` — nodes auto-added by NetworkX
  - Create reverse edge: `G.add_edge(end_node, start_node, key=f"PW_{feature_id}_R", ...,
    geometry=LineString(reversed(geom.coords)))` (ADR-0004 §7)
- Validate: no self-loops (`G.number_of_selfloops() == 0`)
- Compute stats: node count, edge count, mean degree, isolated nodes (degree 0), connectivity by
  level
- Return `(G, stats)`

### Step 4: Add within-level connectivity analysis (0.5 day)

- For each `level_id` in the `level_lookup`:
  - Extract subgraph: all edges where `edge['level_id'] == level_id`
  - Convert to undirected for connectivity check: `G_undirected = subgraph.to_undirected()`
  - Count connected components: `nx.number_connected_components(G_undirected)`
  - Largest component size: `max(len(c) for c in nx.connected_components(G_undirected))`
  - Store in `stats['connectivity_by_level'][level_id] = {component_count, largest_component_size}`
- Log summary: `"Level AQ 3000: 1 component (1453 nodes)"`

### Step 5: Serialize graph, node_map, and stats to disk (0.5 day)

- Write `G` to `build/graph_raw.pkl` using `pickle.dump(G, file, protocol=5)` (ADR-0004 §8)
- Write `node_map` to `build/node_map.pkl` using `pickle.dump(..., protocol=5)` for DT-006
  consumption
- Add metadata to `stats`: `etl_version`, `timestamp` (ISO 8601 UTC per ADR-0004 §9), `z_range_by_level`
- Write `stats` to `build/graph_raw_stats.json` with full schema per ADR-0004 §10:
  `{etl_version, timestamp, node_count, edge_count, mean_degree, self_loops_removed, self_loop_fids,
  isolated_nodes, levels_processed, connectivity_by_level, z_range_by_level, warnings}`
- Add `make etl-graph-raw` target to `Makefile`:
  ```makefile
  etl-graph-raw:
      @echo "Building raw pathway graph..."
      docker compose -f infra/docker-compose.yml run --rm etl sh -c \
          "pip install -e packages/wayfinding[dev] && python -m wayfinding.etl.graph"
  ```
- Add `if __name__ == '__main__':` block to `graph.py` for CLI invocation

### Step 6: Z coordinate logging and audit (0.5 day)

- For each level, compute Z statistics from all pathway/transition endpoints before snapping
- Add to `stats['z_range_by_level'][level_id] = {min, max, mean, stddev}`
- Log if any level has Z range > 5 m (likely data issue — Z should be ~constant within a level)

## 6. Data-QA Checks

Run after `make etl-graph-raw` succeeds, before closing the ticket.

1. **Artifact existence:**
   - `build/graph_raw.pkl` exists, size 5–20 MB (rough)
   - `build/graph_raw_stats.json` exists, valid JSON
2. **Node/edge counts in expected ranges:**
   - 10,000 < nodes < 20,000
   - 40,000 < edges < 50,000
   - Mean degree 4–6 (most nodes are junctions or pathway endpoints)
3. **No isolated nodes:**
   - `graph_raw_stats.json → isolated_nodes: 0`
4. **Self-loops removed (if any):**
   - If `self_loops_removed > 0`, list FIDs in `self_loop_fids` and investigate in QGIS (are they
     real micro-loops or snapping artifacts?)
5. **Connectivity by level:**
   - Each level has 1–3 components (main network + possibly detached wings)
   - If any level has >5 components, flag for data investigation (likely disconnected sub-areas)
6. **Z range sanity:**
   - Within each level, Z range < 5 m (levels are horizontal planes, Z should be ~constant)
   - If any level has Z range > 5 m, log a data-QA warning

## 7. Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **1 cm snapping merges distinct junctions (<1 cm apart)** | Low | High — incorrect topology | Acceptable trade-off: CAD data at sub-cm precision is noise. If found in QA, tighten to 0.5 cm (5 mm). Test `test_snap_nodes_precision` will catch rounding errors. |
| **Self-loops from snapping (feature endpoints snap to same node)** | Medium | Low — excluded by AC4 | Detected and logged with FID list; removed from graph. Data-QA investigates if count > 10. |
| **Isolated nodes (degree 0) indicate snapping bug** | Low | High — data corruption | Hard build failure (AC5). All pathways should connect; isolation implies bug in node identity logic or corrupted source data. |
| **Memory exhaustion (45k edges × 2 Shapely geometries each)** | Low | High — OOM crash | Peak memory ~500 MB for geometries + graph. Container has 2 GB default; increase to 4 GB in `docker-compose.yml` if needed. |
| **Pickle deserialization fails across Python versions** | Low | Medium — breaks DT-006+ | Use `protocol=4` (Python 3.4+, compatible with 3.12). Test `test_graph_pickle_roundtrip` validates. If issue persists, add a JSON export option (nodes/edges as lists). |
| **Transition endpoints not in node_map (DT-006 failure)** | Low | High — DT-006 blocked | **Fully mitigated by ADR-0004 §3:** DT-005 snaps ALL endpoints (pathways + transitions) into `node_map` and serializes to `build/node_map.pkl`. DT-006 loads `node_map.pkl` and looks up transition endpoints without re-snapping, ensuring exact coordinate match. |
| **Bidirectional edge storage doubles memory and pickle size** | Low | Low — acceptable | 45k directed arcs vs 22.5k undirected edges is a 2× increase, but still <1 GB. Benefit: uniform handling of directed transitions in DT-006. |
