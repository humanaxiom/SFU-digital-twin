# DT-017 — Reconcile multipart pathways and revised identities

Status: planned. Dependency: DT-016's executable review and isolated baseline.

## Concrete problems

Eleven legacy/revised AQ3000 pathways store connected multipart chains in reversed
part order: FIDs 9321, 9328, 9332, 9333, 9346, 9347, 9348, 9352, 9353, 9354, 9356.
The current graph code concatenates stored coordinates. Seven of these become
self-loop exclusions; four (9332, 9333, 9346, 9347) retain 41 non-source join segments
in accepted contracted artifacts, with confirmed cost/geometry disagreement.
Source-review's `discontinuous_multipart` reason means noncontiguous stored
part order, not proof that the source parts are physically disconnected.

Separately, revised adds 141 pathways (FIDs 22427–22567) without facility/level IDs.
Their vertical-order values and geometry alone do not establish their assignments.

## Ordered implementation

1. Write an ADR for deterministic multipart handling. For a single unbranched
   chain, preserve every original segment and derive a consistent connected order;
   explicitly resolve orientation against endpoint identity and bidirectionality.
   Reject ambiguous, branched or disjoint parts. Never insert a gap segment.
2. Demonstrate failures with reversed-order, branching, disjoint, closed-loop and
   single-part fixtures. Build corrected artifacts only in a new experiment.
3. Compare legacy versus corrected graph edges, distance/geometry consistency,
   room anchors and gained/lost reachable room pairs for both profiles. Publish
   exact affected source FIDs, output hashes and geometry evidence. Define a new
   measured baseline if connectivity changes; do not force historical 816/840 counts.
   Extend the comparison command to preserve and compare independently verified
   manifests with differing code fingerprints; keep same-build stage drift checks.
4. Reconcile the 141 revised additions using authoritative source attributes or
   reviewed mapping evidence. Model any outdoor network separately. Preserve an
   auditable mapping manifest; unknown assignments remain excluded from ingestion
   with explicit diagnostics, not silently repaired or promoted.
5. Rebuild and compare revised routing only after its admission checks pass.
   Supplemental entrance/door/ramp data remains profile-only until its own schema,
   level mapping and provenance contract is accepted.

## Acceptance

No source edits or automatic accepted-artifact replacement. Every routed geometry
segment comes from an original pathway/transition segment; every assigned facility
and level has provenance. Tests, isolated source/build evidence, profile-specific
reachability comparison and independent large-model GIS review are required before
any proposed promotion. DT-016 provides the runnable baseline and comparison tools.

Before declaring green, run a fresh Docker source-to-candidate build and serve the
corrected candidate in an isolated demo for real browser/API route tests. Exercise
affected AQ pathways, the canonical routes, both routing profiles and desktop/mobile
interactions; retain explicit expected changes instead of blindly regenerating
fixtures. Record image/code/source/artifact identities, commands, exits and any
blocked scope. Existing accepted-artifact browser results cannot certify a changed
candidate. Physical LAN acceptance remains a separate requirement.
