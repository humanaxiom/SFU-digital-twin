# DT-020 — Make route availability usable

Status: implemented and verified against the live local demo; see `../reports/DT-020.md`.

The user reports no routes calculate in the otherwise acceptable UI. The live
port-18087 service logs repeated route HTTP409 responses. Four canonical routes
still return200 on that same running server. Both selectors currently offer all
1,017 rooms without connection information; most arbitrary pairs are disconnected.
The exact user-selected pair/profile has been requested and remains pending.

Older demos on ports 18077 and 18097 return the legacy route response without
structured guidance, despite serving current static files. Detect that mismatch
explicitly. Refresh and test the known current demo on port 18087.

Add origin/profile-specific mapped-connection choices so users can find supported
routes. Preserve deliberately selected unsupported rooms and their failure message.
Separate same-anchor results (no walking path) from actual positive-length paths.
Do not add network edges, change sources, substitute endpoints, or claim physical
accessibility. Current data gaps remain explicit.

Agree an additive read-only route-options contract in an ADR. Implement deterministic
backend availability, client grouping/help text and stale-response guards in parallel.
Demonstrate failing regressions, run affected Docker unit/client/HTTP checks, then
fresh browser/API E2E on final code, including actual connected-destination selection,
unsupported requests, profile changes and mobile. Verify the live demo after refresh.
Record remaining unsupported pairs rather than treating chosen examples as full
network coverage. Obtain independent large-model review before final acceptance.
