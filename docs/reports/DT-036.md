# DT-036 — Floor loading performance and preservation evidence

Date: 2026-11-20
Status: Live verified; independent final review approved

## Diagnosis and isolation

The user reported that restored navigation worked but was extremely slow on
port 18107. The live candidate was idle at the first load check, and no prior
test stacks remained. Recent Strand scene requests took about 1.1 s while route
POSTs took about 30–40 ms. The expensive path was floor construction/transfer.

All unverified changes stayed in `build/experiments/dt036-source`, an isolated
Git checkout of `92674e6`, with read-only candidate artifacts and separate test
services. The live source/service stayed unchanged during the isolated work.
All project execution, parsing, timings and hashing ran in Docker.

## Change 1 — exact driver filtering

The original repository iterated entire unit, detail and landmark layers, then
discarded other floors in Python. The isolated fix applies an exact fixed-field
OGR attribute filter before feature materialization, escapes level-ID string
values, preserves an exact-value Python guard and fails closed on both GDAL
error returns and exceptions. It does not modify source data or add indexes.

Four meaningful RED cases failed before implementation; all four then passed.
They cover unrelated-row visits, exact case/quoted SQL-looking IDs, complete
fields/coordinates/order/null geometry, absent floors and filter failures.
All 22 complete scene records (11 levels × two passes) retained identical
canonical and wire hashes, response sizes and feature counts. Aggregate scene
construction fell from 29.108 to 16.395 s (43.68% less). Serialization remained
about 0.33 s total. Fresh-page browser latency improved 18–54%, but the largest
AQ floors still took about 1.6 s.

Before advancing to change 2, fresh default-click and Preview preservation E2E
both exited 0. A first test reused the measurement client's private address and
hit HTTP 429; the retained failure was superseded by unchanged assertions with
fresh private client addresses. Admission limits were not changed.

## Change 2 — bounded complete response cache

[ADR-0028](../adr/0028-bounded-floor-response-cache.md) defines an artifact/exact-
level cache of complete immutable encoded response bytes. It retains at most
16 responses / 32 MiB, with LRU eviction and no response truncation. Current
11-floor scene bodies total about 14.6 MB. Oversized responses remain fully
available without retention. Bounds cover retained payloads, not peak process
construction memory.

Per-key futures deduplicate concurrent misses. Construction and waiting occur
outside the cache bookkeeping lock, so a cached floor is not blocked by another
floor's slow miss. One captured repository supplies the key, scene and provenance;
OGR handles stay local. Failures wake waiters, are not cached and remain retryable.
Normal CLI startup best-effort prepares up to the bounded recorded-floor set.
Catalog/floor prewarm failures cannot remove foreground access. Programmatic
`create_server` remains lazy. The response API, geometry, ordering, metadata,
browser cache headers, limits and route algorithms remain unchanged.

The repeated-HTTP construction regression failed before implementation, and
10 cache contract tests then passed: response bytes/metadata, concurrency,
warm-hit access during a blocked cold miss, identity, immutability, LRU bounds,
oversized data, retry and bounded best-effort warmup.

## Complete response preservation

A private frozen-baseline server and optimized server served all 11 level APIs
to `tools/dt036_http_scene_compare.py`. Every complete HTTP body matched
byte-for-byte, including geometry, record order, limitations and provenance.
This is stronger than comparing only feature counts. The baseline clone was
removed after comparison. Examples: AQ 6000 retains all 263 rooms, 16,316 detail
features and six landmarks in its full 4,635,852-byte HTTP body.
